# Share-link image (Open Graph / Twitter Card)

Delivery assets: `public/og/fr.png`, `public/og/en.png`, `public/og/ar.png`
(1200×630, one per site locale). Wired into every public page's metadata via
`ogImagePath()` (`lib/i18n/config.ts`) — see `app/[locale]/page.tsx`,
`blog/page.tsx`, `contact/page.tsx`, `blog/[slug]/page.tsx`.

## Why these are pre-rendered files, not `next/og`

The obvious approach — a code-based `opengraph-image.tsx` using Next's
`ImageResponse` (`next/og`) — was tried first and abandoned. In this project,
`ImageResponse` **silently ignores custom fonts** passed via its `fonts`
option: no error, no throw, it just falls back to `@vercel/og`'s bundled
default (Geist), regardless of font format (both `.woff` and converted `.ttf`
were tested) and regardless of rasterizer (`sharp`, when installed, is
auto-preferred by `@vercel/og`; the WASM `resvg` path was also tested by
temporarily removing `sharp` — same result either way).

This was confirmed with a minimal control case: a bare `<div>` rendering
`INTER TEST V2` in the distinctly rounded, geometric Inter typeface, then in
the unmistakably cursive Pacifico — both rendered as the exact same generic
fallback font, byte-for-byte similar output regardless of which font file was
declared. A hand-built SVG with an embedded `@font-face` data URI, rasterized
directly through `sharp` (bypassing satori entirely), showed the same
failure — so this isn't a satori-specific bug, it's the underlying
rasterizer (librsvg via libvips) not honoring embedded/custom fonts on this
stack.

A real browser (tested via Chromium DevTools Protocol) renders `@font-face`
correctly, as expected. So the image is generated by having an actual
browser paint an HTML page and screenshotting it — not by asking a
Node-side SVG/PNG library to lay out text in a custom font.

## Regenerating

Run after any change to `messages/*.json`'s `hero.titleLine1` /
`titleLine2` / `titleAccent` / `leadMobile` (the copy baked into the image),
or to the logo / brand colors:

```bash
node scripts/build-og-cards.mjs
# or, if no Chrome/Edge is found at a standard install path:
node scripts/build-og-cards.mjs --browser "C:\path\to\msedge.exe"
```

This re-reads `lib/og-fonts/*.ttf` (the brand fonts, see below) and
`lib/og-fonts/logo-mark.png` (the logo, rasterized from
`public/brand/ifriqiya-star.svg`), builds the HTML card, screenshots it with
a locally installed headless Chromium/Edge, and overwrites the three PNGs.

## `lib/og-fonts/`

TTF files for Nunito Sans (headings, fr/en) and Cairo (headings + body, ar —
Nunito Sans has no Arabic glyphs) and Poppins (body, fr/en), plus the
rasterized logo mark. Downloaded once from Google Fonts and committed rather
than re-fetched on every build.

One non-obvious step: Google Fonts no longer serves bare `.ttf` over its CSS
API regardless of the User-Agent sent (the classic "old Safari UA" trick
returns `.woff`, not `.ttf`, as of this writing) — the files here were
decompressed from that `.woff1` container into genuine SFNT/TTF (a WOFF1 file
is just a header + zlib-compressed SFNT tables; reconstructing the original
is a well-defined, from-scratch operation, done once and not repeated here).
This conversion turned out to be unrelated to the actual font-ignoring bug
above (both the `.woff` and the converted `.ttf` failed identically through
`ImageResponse`), but the `.ttf` files are what `scripts/build-og-cards.mjs`
now reads, since real `.ttf` is the more broadly compatible format and the
conversion is already done.
